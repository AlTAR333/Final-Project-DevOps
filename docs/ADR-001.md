# ADR-001: Transaction boundary and idempotency

Owner: Tristan
Status: Accepted

## Context

`POST /api/v1/orders` must reserve stock exactly once, even when:

- the client retries the same request,
- several identical requests (same `Idempotency-Key`) arrive at the same time on different API replicas,
- many clients compete for the last units of a product,
- the API process restarts between a request and its retry.

The API runs as two replicas, so any lock or cache held in process memory is useless: the only state shared by both replicas is PostgreSQL. The contract also requires the `202` response to be sent only after the order, the stock reservation and the work item for the worker are durably committed.

## Decision

### One database transaction per order

`api.orders.place_order` runs everything in a single PostgreSQL transaction (default `READ COMMITTED` isolation):

```
BEGIN
  INSERT INTO orders (order_id, idempotency_key, request_hash, ...)
    ON CONFLICT (idempotency_key) DO NOTHING
    RETURNING order_id
  if no row returned  -> this key already has an order:
        same request_hash      -> return the existing order_id (replay)
        different request_hash -> 409 IDEMPOTENCY_CONFLICT
  for each SKU, in sorted order:
        UPDATE products SET available = available - qty
         WHERE sku = $sku AND available >= qty
         RETURNING unit_price_cents
        no row returned -> 409 OUT_OF_STOCK, whole transaction rolls back
  UPDATE orders SET total_cents = ...
  INSERT INTO order_lines (...)
  INSERT INTO jobs (order_id)
COMMIT
```

The order, its lines, the stock decrement and the job row either all exist or none do. The `jobs` row acts as a transactional outbox: the worker can never see an order that was not committed, and a committed order always has a job.

### Why each piece is there

| Mechanism | Guarantee |
|-----------|-----------|
| `UNIQUE (idempotency_key)` + `ON CONFLICT DO NOTHING` | At most one order per key, across all replicas. When 8 identical requests race, PostgreSQL makes 7 of them wait on the unique index until the first commits; they then insert nothing and read the winner's `order_id`. |
| `request_hash` (SHA-256 of the JSON body with sorted keys) | Detects reuse of a key with a different payload. Key order in the JSON does not matter; item order and values do. |
| Conditional `UPDATE ... WHERE available >= qty` | Checking and decrementing stock is one atomic statement, so two transactions cannot both see "1 left" and both take it. The row lock taken by the update serialises competing orders per SKU. |
| `CHECK (available >= 0)` | Last line of defence: even a bug in the code cannot store negative stock. |
| Lines aggregated before reservation | `KIT-100 x3` twice is reserved as one `KIT-100 x6`, so limits and stock are checked against the real total. |
| SKUs locked in sorted order | Two multi-SKU orders always lock rows in the same order, which removes the A-waits-for-B / B-waits-for-A deadlock. |
| Any error inside the transaction rolls everything back | No partial allocation: if the second SKU is out of stock, the first SKU's decrement is undone. |

### Edge cases decided

- **Replay after completion:** a replay returns the original `order_id` with `status: queued` (an acceptance receipt), as the contract asks, without touching stock.
- **Key of a rejected request:** an `OUT_OF_STOCK` request commits nothing, including its key, so the client may retry the same key later.
- **Restart:** the idempotency mapping lives in the `orders` table, so a replay after an API restart behaves exactly like one before it.

## Consequences

- Correctness depends only on PostgreSQL constraints and row locks, so it holds for any number of API replicas.
- Hot SKUs are serialised by their row lock. That is acceptable at this scale (dozens of requests per second); at much higher volume we would shard stock or reserve in batches.
- Same-key requests wait for the first transaction to finish, so a slow first request delays its duplicates. The transaction is short (a handful of statements), so the wait is milliseconds.
- `available` is the single source of truth for stock; there is no separate inventory table to keep in sync.
- Stock reserved by an order that later fails in the worker is **not** returned automatically; it stays reserved for manual review, as the brief requires.

## Evidence

| Test | What it proves |
|------|----------------|
| `tests/race/test_same_key.py` | 8 threads, same key and payload: one order, one `order_id`, stock decremented once, one job. |
| `tests/race/test_distinct_keys.py` | 12 and 30 threads competing for 5 units: exactly 5 accepted, the rest `OUT_OF_STOCK`, stock ends at 0. Opposite-order multi-SKU orders complete without deadlock. |
| `tests/integration/test_order_flow.py` | Replay, replay on a new connection, payload conflict, multi-SKU rollback, duplicate-line aggregation. |

Removing `AND available >= qty`, the `ON CONFLICT` clause, or the sorted SKU order each makes these tests fail; this is used as the red-to-green demonstration in CI.
